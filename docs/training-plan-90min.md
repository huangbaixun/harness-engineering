# Harness Engineering 90 分钟入门培训方案

> 面向部门多角色（后端 / 前端 / QA / PM）零基础同事的引导培训。
>
> **设计哲学**：90 分钟内不要妄想讲全；把"为什么需要"讲透 + 让"价值差"在 demo 里被亲眼看到 + 让每个角色找到一个自己想用的入口。

---

## 1. 培训目标与听众画像

### 1.1 听众画像

| 维度 | 默认假设 |
|------|---------|
| 角色 | 后端、前端、QA、PM 混合 |
| AI 编程经验 | 零基础——用过 ChatGPT 聊天，没用过 Claude Code / Cursor 等 agentic 工具 |
| 期望 | "听说 AI 能帮我写代码，但不知道在我的工作里能做什么" |
| 现场设备 | 不预装环境，仅看屏幕 + 纸笔 |
| 顾虑 | "AI 会不会写出 bug 把我坑了"、"我的角色（QA / PM）能用得上吗" |

### 1.2 三层学习目标（按 Bloom 层级）

| 层级 | 目标 | 验证方式 |
|------|------|---------|
| **K — Know（认知）** | 能复述：Prompt → Context → Harness 三阶段；六层模型；一个核心原则 | 现场快速问答 |
| **U — Understand（理解）** | 能解释：为什么"prompt 写得好" ≠ "AI 能可靠工作"；harness 在我的角色里解决什么具体问题 | 纸上动手回答 |
| **D — Do（行动）** | 能列出：自己项目最缺的一层 + 下周会动手尝试的一件事 | 离场调查问卷 |

零基础培训不追求 D 层完整落地，只求**触发尝试动机**。

| 段落 | 时长 | 主题 | 形态 | 占比 |
|------|-----|------|------|------|

| 合计 | **90 min** | | | 100% |

时间分配原则：

- 演示（§D）权重最大（28%），因为零基础最有效的说服方式是亲眼看到差异。

- 互动（§A + §C + §F + §G）合计 36%，对抗"被动听课"。

## 3. 各环节详细设计

### §A 开场 + 三个调研举手（5 min）

**目的**：建立现场基线，让讲师知道接下来该重还是该浅。

**讲师动作**：

1. 30 秒自我介绍 + 一句话定位："今天我要让你看到，AI 写代码这件事不是 prompt 工程的延续——它是一项工程实践。"
2. 三个举手问题，逐一统计：
   - "用过 ChatGPT 写过/改过自己工作中代码的，请举手"
   - "用过 Claude Code、Cursor 这类 agentic 编程工具的，请举手"
   - "曾经因为 AI 给了错代码而花了更多时间排查的，请举手"
3. 第三问通常举手最多——立刻接："今天就是讲这个为什么，以及怎么治。"

**幻灯片**：标题页 + 三问页（动效逐条出现）。

---

### §B 为什么会有 Harness Engineering（15 min）

**目的**：把"AI 编程为什么从 prompt 升到 harness"的演进逻辑讲清，听众听完能复述三阶段。

**核心结构**：从"模型不会出错的妄想"到"工程化包裹模型"的演进。

**4 张关键图（必须配 PPT）**：

#### 图 1 — 三阶段演进时间轴

```
2022──2024              2025                    2026──
──────────────────────────────────────────────────────
Prompt Engineering   Context Engineering   Harness Engineering
（写好提示词）       （喂对上下文）        （设计反馈系统）
   ↑                    ↑                    ↑
单次推理            多轮 RAG / 工具       系统级约束 + 验证
```

**讲法**：
"我们对'让 AI 干活'这件事的理解，三年里跳了三次。第一阶段觉得是话术问题——只要 prompt 写对，模型就能输出对的东西。第二阶段发现不行，得给上下文。但今天我们发现，光有上下文也不够——模型会忘、会跑偏、会在第十个 feature 突然把第三个 feature 的代码改坏。这才出现第三阶段：你不是在写 prompt，你是在搭建一个让 AI 可以可靠工作的环境，这个环境就叫 harness。"

#### 图 2 — 骏马与缰绳的隐喻

```
  ┌─────────────┐         ┌─────────────────┐
  │   骏马      │         │  缰绳 / 鞍具    │
  │  (Model)    │ ────→   │   (Harness)     │
  │  力量强但   │         │  引导力量朝     │
  │  不知方向   │         │  正确方向       │
  └─────────────┘         └─────────────────┘
```

**讲法**：
"Anthropic 的工程师有个比喻：模型是骏马——力量惊人，但它不知道你想去哪。Harness 是缰绳和马鞍。你不是把马训得听话（模型已经训完了），你是给它装上你能控制的工具。这个比喻对零基础同事最直观——你今天不是来学怎么和马说话，是来学怎么装马具。"

#### 图 3 — 一次"AI 失败"的真实剖面

```
任务：「在 todo 应用里加一个删除按钮」

Round 1: AI 加了删除按钮 ✓
Round 2: 用户说"删除前要弹确认框"
         AI 加了确认框 ✓
         但顺手把所有按钮的颜色改成了红色 ✗
Round 3: 用户说"你为什么改颜色"
         AI 说"我以为你想要警告样式"
         撤回颜色改动 ✓
         但顺手删掉了之前的确认框逻辑 ✗
Round 4: ...用户决定自己写。
```

**讲法**：
"这是一个真实的、典型的'AI 越用越累'的场景。问题不在 AI 笨——它每一步都看似合理。问题在你跟它对话的环境里没有任何机械约束告诉它'未授权的修改禁止'、'颜色变更必须有理由'、'每次改完跑测试'。Harness 就是把这些规则装到环境里，模型不需要自己记得，环境会强制。"

#### 图 4 — Harness Engineering 的目标转变

```
工程师的工作重心
        ↓
  ┌──────────────────┬──────────────────┐
  │  传统工作         │  Harness 时代     │
  │                  │                  │
  │  写代码           │  设计 AI 可以可靠 │
  │                  │  工作的环境        │
  └──────────────────┴──────────────────┘
```

**讲法**：
"这话听起来吓人——'我以后不写代码了？' 不是这个意思。是说，未来你最高 ROI 的事情，是把'AI 在我项目里反复犯的错'转化成机械化的规则，让它不再犯。你不是被 AI 替代，你是变成 AI 团队的'马具工程师'。"

**讲师过渡**："那这个'环境'到底长什么样？这个那个的具体抱怨我们各角色都有，下面用 4 个角色的案例来说。"

### §C 没有 harness 的 4 个角色痛点（10 min）

**目的**：让每个角色都看到一个"是的我也遇到过"的具体例子。

**结构**：4 个角色 × 1 个具体案例 × 1 句"harness 怎么治"。每个 ~2 分钟。

#### C1 后端 — 过度实现

**痛点**：
> "让 AI 加个 user 删除接口，它顺手把整个 user model 重构了，还引入了一个新依赖 `redis`。我只想加一个 endpoint。"

**harness 怎么治**：
- features.json 里 `out_of_scope` 字段明确禁止重构和加依赖
- harness:plan 强制声明改动范围，超出范围的改动会被 verify 阻挡
- Stop Hook 检查 dependencies diff，发现新依赖直接 fail

#### C2 前端 — 样式偏移

**痛点**：
> "让 AI 加个 modal，它把全局 css 变量改了。整个 app 颜色都变了，回滚要找半小时。"

**harness 怎么治**：
- PreToolUse Hook 拦截对全局样式文件的修改，需要用户显式确认
- harness:plan 里 `forbidden_patterns` 声明禁止改 `tokens.css`
- /careful 模式包裹破坏性广播变更

#### C3 QA — 测试缺位

**痛点**：
> "AI 改完代码说'已实现'，但你去看根本没加测试。你提它，它说'下次补'，下次也没补。"

**harness 怎么治**：
- harness:tdd 强制 Red-Green-Refactor，没测试不能进 Green
- Stop Hook 拒绝任何"代码改了但 test 文件没改"的 diff
- harness:audit 给项目打分，测试缺位会显示在七维度报告里

#### C4 PM — 决策追溯丢失

**痛点**：
> "三个月前为什么我们选 Kafka 不选 SQS？AI 当时给了一份分析，但聊天记录早被冲掉了。现在团队在讨论换型，没人记得当时的理由。"

**harness 怎么治**：
- ADR（架构决策记录）作为活文档归档，PR 合入前必须落地
- harness:archive 把每个 feature 的 proposal / design / tasks 永久归档
- 三个月后任何人 grep 关键词都能找到当时的决策上下文

**讲师过渡**："4 个角色 4 种痛——共同点是，问题不是 AI 笨，是 AI 工作的环境没有约束。下面我直接演示加和不加约束差多少。"

### §D 现场对比 demo（25 min）—— 重头戏

**目的**：让"价值差"在 25 分钟内被亲眼看见。

**Demo 项目**：mini 留言板 web 应用（参见 §3.5 demo 详细脚本）。

#### 整体走路

| 段落 | 时长 | 内容 |
|------|-----|------|
| D.1 | 3 min | 演示项目说明 + 任务陈述 |
| D.2 | 8 min | **Baseline 路径**：裸 Claude Code，没装 harness |
| D.3 | 10 min | **Treatment 路径**：装上 harness-engineering，跑 plan → tdd |
| D.4 | 4 min | 对比讨论：让听众说差在哪 |

#### D.1 项目与任务（3 min）

**项目**：一个已有的 mini 留言板，包含留言列表、添加留言、删除留言。代码 ~150 行。

**任务**：『为留言加"点赞"功能。每条留言可以点赞，重复点赞会取消。点赞数超过 5 的留言用金色高亮。』

讲师对听众说：
"这个任务对一个有经验的开发者来说，30 分钟。我们看 AI 怎么做。两条路径，同一个任务，同一个 Claude 模型，唯一区别是装不装 harness。"

#### D.2 Baseline 路径（8 min）

**演示走路**：

1. 打开裸 Claude Code，输入任务描述。
2. AI 立刻开始改代码（**演示要点**：故意不询问、不澄清）。
3. 5 分钟左右 AI 完成第一版，列出："我加了点赞按钮、点赞数显示、金色高亮、还顺便重构了一下数据存储改用了 localStorage。"

**让听众发现的"AI 失误"**（讲师明示）：

- ❌ 没问"重复点赞取消"的具体语义（同 IP？同 user？同 session？）
- ❌ "顺便"重构 localStorage——不在任务范围内
- ❌ 没写测试
- ❌ 没区分"取消点赞"和"减一个赞"的边界情况
- ❌ 改完之后没跑既有测试，已有的"删除留言"功能其实被这次重构搞坏了（讲师故意提前埋雷）

**讲师收尾**："你看，AI 不是不努力——它每一步都'自以为合理'。但没有 harness 框住它，它就会四面开花。30 分钟下来，你拿到的不是一个 feature，是一堆要回滚的改动 + 一个新 bug。"

#### D.3 Treatment 路径（10 min）

**演示走路**：

1. 切到装好 harness-engineering 的同一个项目。
2. 输入相同任务，但通过 `/harness:plan` 触发。
3. AI 进入 **clarify 阶段**——主动问：
   - "重复点赞按什么维度去重？"
   - "金色高亮是只在前端样式还是要加到数据模型？"
   - "你希望保留 localStorage 还是切到 server？"
4. 演示用户回答这些问题（讲师扮演用户）。
5. AI 进入 **plan 阶段**——产出 features.json：
   ```json
   {
     "name": "like-feature",
     "acceptance_criteria": [
       "每条留言展示当前点赞数",
       "点击点赞按钮 +1，再次点击 -1",
       "点赞数 > 5 的留言金色高亮"
     ],
     "out_of_scope": [
       "不切换存储后端",
       "不重构既有 model",
       "不加新依赖"
     ],
     "dependencies": []
   }
   ```
6. AI 进入 **tdd 阶段**——先写失败测试（红），再写最小实现（绿）。
7. **Stop Hook 拦截一次**：AI 试图绿色阶段时一次性写超过 30 行代码，hook 提示"分步太大"，AI 拆细。
8. AI 进入 **verify 阶段**——所有 acceptance criteria 逐项过，原有测试也跑了，没有回归。
9. 最后产出 PR：3 个 commit（red / green / refactor），一份归档的 design doc，一个干净的 diff。

**让听众发现的差异**（讲师明示）：

- ✅ 主动澄清，不假设——节省后续返工
- ✅ scope 被锁定——「不切存储后端」写在 out_of_scope 里，模型再"自以为合理"也无法越界
- ✅ 测试先行——绿色才能合入
- ✅ 既有功能保护——所有原测试一起跑
- ✅ 归档可追溯——三个月后还能查"当时为什么这么做"

#### D.4 对比讨论（4 min）

讲师问开放问题（举手作答即可）：

1. "Baseline 路径里，AI 哪一步开始走偏？" → 期待答案："一开始就没问，直接动手"
2. "Treatment 路径里，最让你意外的是哪一点？" → 期待答案：rigid 边界 / 测试拦截 / 归档
3. "如果今天给你一个 baseline 路径产出的 PR 来 review，你会怎么处理？" → 引出 review 成本话题

**讲师过渡**："这就是 harness。你看到的不是一个工具，是一套包裹工具的工程化框架。下面 15 分钟我把它的骨架讲清楚，让你知道下次自己怎么搭。"

### §E 三原则 + 六层模型 + 反馈循环（15 min）

**目的**：建立词汇表，让听众离场时能复述核心概念。

**结构**：3 + 6 + 1 = 三块，每块 5 分钟。

#### E.1 三大核心原则（5 min）

```
1. 永远不要让创建者独立评审自己的产出
   → 写代码的 Agent ≠ 评审代码的 Agent

2. 上下文重置优于无限压缩
   → 长任务里，定期清空并结构化交接，比累积更有效

3. 约束赋能，不是限制
   → 越严格的边界，AI 输出越可靠（这点反直觉，重点强调）
```

**讲法重点**：第三条最反直觉，要花 1 分钟讲：
"很多人觉得给 AI 加约束是在限制它发挥。但我们的实证刚好相反——你给 AI 越紧的边界，它的输出越靠谱。因为 AI 的失败模式不是'想不出好方案'，是'方案太多收不住'。约束等于决策——你帮它决定了，它就专心干活。"

#### E.2 六层模型（5 min，配 §3.4 图）

#### 图 5 — 六层模型

```
┌──────────────────────────────────────────────────┐
│  ① 记忆层 (Memory)        CLAUDE.md               │
│     静态知识：架构约定、禁止规则、测试命令         │
├──────────────────────────────────────────────────┤
│  ② 规则层 (Rules)         settings.json           │
│     确定性行为：权限、模型、输出配置               │
├──────────────────────────────────────────────────┤
│  ③ 技能层 (Skills)        skills/ + commands/     │
│     按需知识 + 显式工作流入口                      │
├──────────────────────────────────────────────────┤
│  ④ 智能体层 (Agents)      agents/                 │
│     上下文隔离的专用 Subagent                      │
├──────────────────────────────────────────────────┤
│  ⑤ 钩子层 (Hooks)         pre/post/stop hooks     │
│     确定性强制：不依赖模型判断                     │
├──────────────────────────────────────────────────┤
│  ⑥ 工具层 (Tools)         MCP Servers             │
│     能力扩展：外部服务接入                         │
└──────────────────────────────────────────────────┘
```

**讲法**：
"六层不是六个东西并列，是六类能力按强度从弱到强排列。
- 记忆层最弱：模型可能忽略
- 规则层稍强：权限是机械的
- 钩子层最强：模型绕不过

你不需要一上来就六层全做。我们的建议路径是：先把 ① 记忆层写好（一份 CLAUDE.md），痛点最大的地方加一层 ⑤ 钩子。其他按需补。"

#### E.3 核心反馈循环（5 min）

#### 图 6 — Harness 演化循环

```
       Agent 失败
          │
          ▼
   ┌───────────────┐
   │ 识别缺失能力   │
   └───────┬───────┘
           │
           ▼
   ┌───────────────────────────────┐
   │ 工程化修复                     │
   │ ├ 更新 CLAUDE.md（记忆）       │
   │ ├ 加 Hook（钩子）              │
   │ ├ 写 Skill（技能）             │
   │ └ 改架构约束                   │
   └───────┬───────────────────────┘
           │
           ▼
   该类失败永不再发生
```

**讲法重点**："这是 harness engineering 的灵魂。
- 普通用法：AI 写错了，骂两句，下次它换个错误重新犯一遍
- harness 用法：AI 写错了，把这个错误转化成一条机械规则，加到环境里

每个失败都不是事故，是免费的 harness 改进材料。你的项目用得越久，AI 在你这里失败率越低——因为环境一直在累积它'撞过的墙'。"

### §F 纸上动手：四角色头脑风暴（10 min）

**目的**：在没有电脑的前提下，让每个人想清楚"自己要怎么用"。

**形式**：发一张 A4 工作纸，5 分钟独立写 + 5 分钟分组讨论。

#### F.1 工作纸题目

**题目**：
> 回想你过去一个月里，AI（ChatGPT / Copilot / Cursor / 任何）让你失望或返工的一个具体场景。
> （场景越具体越好，"AI 写代码不靠谱"不算具体。）
>
> 然后回答三个问题：
>
> 1. 这次失败，AI 是缺了什么"上下文"，还是缺了"约束"？
> 2. 如果让你给这种失败设计一道护栏，你会放在六层里的哪一层？
>    - ① 记忆（写在文档里告诉 AI）
>    - ② 规则（settings 配置）
>    - ⑤ 钩子（自动拦截）
> 3. 这道护栏如果落地，你预估每月能省你多少小时？

#### F.2 多角色提示卡

为四个角色各准备一张提示卡，启发那些一时想不到例子的人：

**后端卡**：
> 提示：API 改动 / 数据库迁移 / 依赖引入 / 错误处理 / 日志规范

**前端卡**：
> 提示：组件样式 / 状态管理 / 全局变量 / 浏览器兼容 / 路由

**QA 卡**：
> 提示：测试覆盖 / 边界用例 / 回归保护 / mock 数据 / 测试命名

**PM 卡**：
> 提示：需求边界 / 决策记录 / 优先级声明 / scope 漂移 / 沟通归档

#### F.3 讨论

3-4 人一组，每人 1 分钟分享自己的答案，组里选 1 个最典型的，讲师挑 2-3 组上台说。

讲师收尾："你们刚刚做的事情，就是 harness engineering 最核心的动作——把一次失败转化成一道机械护栏。今天回去如果你只能记一件事，就记这个。"

### §G 落地路径 + Q&A + 离场问卷（10 min）

#### G.1 落地路径（5 min）

**给个人的"今天就能做的三件事"**：

| 时间 | 动作 | 难度 |
|------|------|------|
| 本周 | 给自己常用的项目写一份 CLAUDE.md（30 分钟，60 行以内） | ⭐ |
| 本月 | 把今天工作纸里写下的那个"失败"，做成一个 Hook 或一条 CLAUDE.md 规则 | ⭐⭐ |
| 本季度 | 跟着 harness-engineering 的 init / audit skill，把项目跑一遍体检 | ⭐⭐⭐ |

**给团队的渐进式路径**：

```
Week 1: 一份 CLAUDE.md（最小可用）
   ↓
Week 2-4: 加 1-2 个 Hook（针对最高频失败）
   ↓
Month 2-3: 引入 skills（plan / tdd / audit）
   ↓
Month 4+: 引入 ADR、归档机制、多 agent 协作
```

讲师重点：「不要一上来就六层全做。先一层，看效果，再一层。」

#### G.2 Q&A（4 min）

预设 3 个最可能被问的问题：

**Q1: "我们公司用 GitHub Copilot / 通义灵码，不是 Claude Code，这套还能用吗？"**
A: 概念全部通用——记忆文件 / Hook / Skill 这些抽象在每个 agentic 编程工具上都有等价物。Claude Code 上是 CLAUDE.md + .claude/，其他工具换成对应路径即可。

**Q2: "学这套的成本有多高？"**
A: 第一份 CLAUDE.md 半小时。第一个 Hook 1-2 小时。完整 harness 1-2 周。但收益是非线性的——每加一层，AI 失败率下降一档。

**Q3: "AI 越来越强，未来这些 harness 是不是不需要了？"**
A: 部分会。harness-engineering 第三原则就是"随模型进化精简 harness"。但这不是说 harness 会消失——失败模式会变，约束的形态会变，"用工程包裹模型"这件事会一直在。

#### G.3 离场问卷（1 min）

二维码扫码 / 纸条收集，问三个问题：

1. 今天最有触动的一点是什么？（开放）
2. 你下周会动手做的一件事是什么？（开放，可空）
3. 想要后续培训覆盖的话题（多选：深入 Hook / 多 Agent 协作 / harness:audit 实操 / 案例复盘）

> 演示目标：在 18 分钟里，让听众看到"同一个任务，装与不装 harness 的最终产出和过程"完全不一样。

### 4.1 演示前置准备清单（讲师培训前 3 天完成）

- [ ] 准备 sample-board 项目（mini 留言板，~150 行）
  - 仓库结构：`board-baseline/`（无 harness）+ `board-with-harness/`（装 harness-engineering）
  - 技术栈：vanilla HTML + JS + 内存存储（Express 路由），让前后端 PM 都能看懂
  - 已有功能：列出留言 / 添加留言 / 删除留言
  - 已有测试：3 个，覆盖 3 个功能
- [ ] 在 `board-with-harness/` 中：
  - CLAUDE.md 60 行
  - .claude/settings.json 含 PreToolUse / Stop Hook
  - skills/plan, skills/tdd, skills/audit 软链到 harness-engineering 真实实现
- [ ] 录制 baseline 备份视频（~6 分钟）——避免现场网络/API 抖动
- [ ] 录制 treatment 备份视频（~8 分钟）——同上
- [ ] 检查投屏字号 ≥ 18 pt

### 4.2 Baseline 演示走位（8 min 现场）

```
T=0:00  开 board-baseline/，跑 npm test，3 测试全绿
T=0:30  打开 Claude Code
T=0:45  输入：「请加一个点赞功能：每条留言可点赞，重复点赞取消，
         超过 5 个赞用金色高亮。」
T=1:00  AI 直接开干，不澄清
T=1:30  AI 改 index.html，加按钮（演示亮点：故意没问"金色"是啥色值）
T=2:30  AI 改 server.js，加 /like 路由
T=3:30  AI 顺手把内存存储改成 localStorage（不在范围内 ❌）
T=4:30  AI 完成，说 "已实现"
T=5:00  讲师跑 npm test → 原本 3 个测试有 1 个挂了（删除留言被 localStorage 改坏 ❌）
T=5:30  讲师 git diff → 改了 5 个文件，远超必要
T=6:00  讲师停下来，让听众看产出：
        - PR 改了 5 个文件
        - 1 个原测试坏了
        - 没有新测试
        - 没有任何决策记录
T=7:00  讲师问："如果你接手这个 PR review，你估计要花多久？"
T=8:00  收尾，切到 treatment
```

### 4.3 Treatment 演示走位（10 min 现场）

```
T=0:00  切到 board-with-harness/
T=0:30  快速展示 CLAUDE.md 的 60 行：架构约定、禁止规则、测试命令
T=1:30  快速展示 settings.json hooks 配置（一图带过）
T=2:00  Claude Code 中输入：/harness:plan
T=2:30  AI 进入 clarify 阶段，问：
        - 重复点赞的去重维度？
        - 金色高亮要不要加到数据 schema？
        - 是否切换存储？
T=3:30  讲师扮演用户回答：
        - 同 session 去重
        - 不进 schema，纯前端样式
        - 不切存储
T=4:00  AI 产出 features.json，含 acceptance_criteria + out_of_scope
T=4:30  AI 进入 /harness:tdd
T=5:00  AI 写 1 个失败测试（红），show 测试运行失败
T=5:30  AI 写最小实现（绿），show 测试通过
T=6:30  AI 试图加金色高亮时，第一次 commit 改超过 30 行（演示亮点）
        Stop Hook 触发，提示"分步太大"
T=6:45  AI 拆细，重新 commit
T=7:30  AI 进入 verify
T=8:00  show 全部测试通过（包括原 3 个 + 新 2 个）
T=8:30  show git log：red / green / refactor 三个 commit 干净
T=9:00  show .harness/changes/like-feature/ 归档：proposal.md / tasks.md
T=9:30  讲师对比 baseline：
        | 维度 | Baseline | Treatment |
        |---|---|---|
        | 文件改动数 | 5 | 2 |
        | 原测试通过 | 2/3 ❌ | 3/3 ✓ |
        | 新测试 | 0 | 2 |
        | 范围越界 | 是（改存储） | 无 |
        | 决策归档 | 无 | proposal.md ✓ |
        | review 成本 | 高 | 低 |
T=10:00 收尾
```

### 4.4 演示意外的兜底

| 意外 | 兜底 |
|------|------|
| API 抖动 / 网络断 | 切到预录视频 |
| AI 没按预期"出错" | 改用预录视频，承认现场偶尔不复现，强调"长期统计差异" |
| Hook 没触发 | 提前在 sample 里放好"必触发"的输入；备一段已触发的截屏 |
| 听众打断频繁 | 把问题集中到 §D.4 对比讨论环节回答，先把流程跑完 |

## 7. 风险与备选方案

| 风险 | 缓解 |
|------|------|
| 90 min 太紧，§B 或 §E 讲超时 | 预设 §B / §E 各有 1 张"可砍页"，超时立即砍 |
| Demo 现场复现失败 | 预录视频作 plan B；并在讲义里写好"承认 + 切视频"话术 |
| 多角色注意力差异大（PM 听不进代码细节） | §C / §F / §G 角色分桶设计；§D demo 中代码用业务语言旁白 |
| 听众零基础但少数同事很懂 | §G Q&A 留出深度问题接口；下次专题培训的钩子 |
| 90 min 后听众"听完就忘" | §G 离场问卷强制写"下周做的一件事"，30 天后做 follow-up |

## 8. 这份方案没覆盖的（明确说不做）

- 不深入讲 LLM 原理（零基础，且时间不够）
- 不展开各种工具（Cursor / Cline / Aider / Copilot）的对比（除 Q1 外）
- 不讲 harness-engineering 的 ADR / 架构演进史（业内同仁感兴趣，听众不感兴趣）
- 不强推某一具体工具（概念通用，工具名称各平台不同）
- 不安排培训中的实机操作（前置已确认听众不预装环境）
